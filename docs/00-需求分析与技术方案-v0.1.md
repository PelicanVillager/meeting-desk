## 0. 先说结论

**这个产品本质上是一个"本地数据库 + 本地文件库 + 阅读器 + 可选本地 AI"的桌面应用，而不是一个网页。**

三条推论：

1. **必须做桌面应用（Tauri），不做纯网页。** 浏览器沙箱拿不到稳定文件路径、不能调用系统 OCR、不能长期保管几十 GB 材料。用 Tauri 后，"完全本地、断网可用"是天然成立，而不是靠自觉。
2. **核心资产是"关系数据"，不是文件。** 真正的难点在"会议 → 议题 → 主材料 → 附件"这套父子关系，以及"同一份文件被多个议题引用"的多对多关系。文件只是磁盘上的一个 blob。
3. **AI 是可选插件，不是地基。** 没有本地模型时，导入、解析、OCR、分类、检索、阅读、备注必须 100% 可用。这一点要在架构上强制，而不是靠界面提示。

本机环境实测（2026-09-28）：

| macOS 26.6.2 / Apple Silicon | ✅ | 可用系统级中文 OCR |

```
├──────────────────────────────────────────────────────────────┤

├──────────────────────────────────────────────────────────────┤
│ ④ 桥接层  Tauri IPC（强类型 command / event，带进度事件）      │
├──────────────────────────────────────────────────────────────┤
│ ⑤ 本地核心  Rust                                             │
│   导入 · SHA-256 · 内容寻址文件库 · SQLite/FTS5 · OCR 调度     │

├───────────────┬───────────────────┬──────────────────────────┤
│ SQLite + FTS5 │ 本机文件库 blobs   │ 本机进程 / 系统框架       │

        ↑ 全部在本机。唯一允许的出站目标是 127.0.0.1（本地模型）
```

### 1.2 关键架构决策（含理由）

**决策 1：解析重活放前端 Worker，不放 Rust。**
PDF 文本抽取由 pdf.js 在前端直接完成（它有 `getTextContent()`，天然带每页文本与坐标），DOCX/XLSX 用 JS 库解析。这样 Rust 侧**不需要任何 PDF/Office 解析依赖**，架构更瘦、离线打包更简单。代价是解析发生在 webview 内，所以放进 Web Worker 后台跑，不阻塞界面。

**决策 2：Rust 只做四件"只有原生层才能做"的事。**
文件系统（拖入落盘、哈希、内容寻址库）、SQLite + FTS5、系统 OCR 调用、本地 AI 的 loopback 代理与网络守卫。职责少 = 安全面小 = 可审计。

**决策 3：内容寻址存储（CAS），从第一天就做。**
文件按 SHA-256 存成 `blobs/<前2位>/<sha256>.<ext>`，全库唯一一份。用户在两个议题里引用同一份"预算表.xlsx"，磁盘上只有一份，数据库里两条关系。这就是需求第十一条"不要复制文件"的落地方式。

**决策 4：AI 输出必须能在原文中找到。**
AI 给出的每条要点都要带 `文件名 + 页码 + 原句`。系统拿到原句后**在本地已抽取的文本里做归一化匹配**（去空白、全半角统一、标点归一）。匹配不上 → 该条标记"⚠️ 未在原文找到"，默认折叠不展示。这是防编造的机制保障，而不是靠提示词祈求。

**决策 5：结构变更必须留痕。**
任何议题/附件关系都带 `origin` 字段（`manual` / `ai_suggested_confirmed`）。AI 永不直接写结构，只能产出建议，由人点"确认"。右键菜单的每一次手动调整都会写成 `manual`，AI 后续不得覆盖人工结果。

### 1.3 数据流（一次完整导入）

```
拖入 N 个文件
   ↓ Rust：落盘到临时区 → SHA-256 → 查重
   ├─ 已存在同哈希 → 不复制字节，提示"已存在，是否建立新的引用关系？"
   └─ 新文件 → 移入 blobs/<xx>/<sha256>.<ext>（只读，永不被修改）
   ↓ DB：写 documents + meeting_documents（状态=已导入）
   ↓ Worker 解析（并发 2~4，带进度事件）
   ├─ PDF  → 逐页取文本层；判定"无文本层页" → 入 OCR 队列
   ├─ DOCX → 标题/正文/表格 → 按段落编号
   ├─ XLSX → 各 sheet 单元格文本 → 按 sheet+单元格定位
   └─ 图片 → 直接入 OCR 队列
   ↓ 写 page_text，同时投喂 FTS5 索引
   ↓ OCR 队列（Rust + Vision，并发 2）
   └─ 写 OCR 结果（文本 + 坐标 + 置信度）→ 更新 FTS5
   ↓ 材料识别（规则优先，AI 可选）
   └─ 产出"分类候选 / 附件关系候选" → 待确认列表（绝不自动落库）
   ↓ 用户确认 / 手动拖拽 → 写 topic_documents
   ↓ 生成会议目录树（左侧栏）
```

## 3. 用户操作流程

### 3.1 会前：整理

1. 打开应用 → 首页显示 🔒 本地模式 → 拖入整场会议材料（几十到上百份，或直接拖文件夹）
2. 导入抽屉显示逐个文件状态：`已导入 → 解析中 → 已解析 / OCR处理中 / 解析失败（可重试）`
3. 发现同名或同哈希文件 → 提示"已存在相同文件，是否建立新的引用关系？"（不复制）
4. 系统给出**候选结构**（议程、第一议题、各部门议题、主材料、附件），全部以"建议"形式呈现
5. 用户在整理台确认/修改：右键设为会议议程/第一议题/议题/附件/其他；拖拽把附件挂到议题下；改附件编号（附件1 / 附件一 / 附件A）
6. 形成会议目录树 → 点【进入会议模式】

### 3.2 会中：阅读 + 记录

1. 左栏点议题 → 中栏显示主材料，右栏可切附件 / AI 摘要 / 备注
2. 附件点击即开，不需要回列表找（附件区高亮当前项）
3. 快捷键：`←` 上一议题、`→` 下一议题、`Space` 下一份材料、`Esc` 退出阅读模式、`⌘K` 搜索
4. 随时记录：
   - 选中正文文字 → 右键/快捷键 → 针对该段加备注
   - 页级备注（"第 3 页：领导要求补充预算数据"）
   - 议题级备注、会议级备注
5. 所有操作自动保存；阅读位置（会议/议题/材料/页码/缩放/滚动）持续记录
6. 异常退出 → 重开 → 顶部提示恢复上次位置

### 3.3 会后：复盘

1. 点【生成会议工作记录】→ AI 汇总"材料 + 会议期间我的备注"
2. 输出分两块：会议事项、待办事项（缺责任部门/截止时间时明确写"未明确"）
3. 每条事项都可点击回溯到来源材料与页码
4. 【加入我的一页纸】按钮预留（第一阶段只落 Task 表 + 导出 JSON，不做跨系统同步）

### 3.4 搜索流程

`⌘K` → 输入"预算" → 结果按来源分组标注：

```
找到 8 个结果
```

## 4. 数据模型

SQLite + FTS5。所有表带 `created_at / updated_at`，所有写入走事务（这是"自动保存"的基础）。

### 4.1 实体表

### 4.2 全文索引

```sql
CREATE VIRTUAL TABLE search_fts USING fts5(
  document_id UNINDEXED,
  source,               -- original | ocr | note | ai
  page_no UNINDEXED,
  body,
  tokenize = 'trigram'  -- 中文/英文/中英混排均可子串匹配
);
```

选 `trigram` 分词器的理由：SQLite 默认分词器不切分中文，连续中文会变成一个 token，导致"预算"搜不到"关于预算的说明"。trigram 支持子串匹配，中英文都适用。限制是**查询词少于 3 个字符时无法走索引**，此时回退 `LIKE` 扫描（本场景单场会议几十万字，扫描可接受）。若后续需要更精细的中文分词与排序，可再加一列用 Apple `NLTokenizer` / jieba 分词后索引。

### 4.3 关系图

```
meetings ─┬─< topics ─┬─< topic_documents >─┬─ documents >─ blobs(sha256)
          │           │                     │
          │           │                     ├─< page_text
          │           │                     ├─< text_blocks
          │           │                     ├─< annotations
          │           │                     └─< ai_citations
          ├─< meeting_documents >───────────┘
          ├─< annotations (scope=meeting)
          ├─< ai_results ─< ai_citations
          ├─< ai_suggestions
          ├─< tasks
          └─  reading_state
```

设计要点：**documents 是全局实体，不属于任何会议。** 同一份文件跨会议出现时，blob 与 document 都只有一条；会议归属、议题角色、备注、AI 结果都属于"关系"或"上下文数据"。

## 5. 文件关系模型

### 5.1 三层分离

| 层 | 存什么 | 存哪 |
| --- | --- | --- |
| **内容层** | 文件字节，SHA-256 命名，只读 | 文件系统 `blobs/` |
| **材料层** | 文件名、类型、页数、哈希、原路径、解析状态 | SQLite `documents` |
| **关系层** | 属于哪场会议、在哪个议题里、是主材料还是附件几、排序、编号 | SQLite `meeting_documents` / `topic_documents` |

**这就是"文件只有一份、关系可以有很多份"的实现。**

### 5.2 去重规则

```
新文件 → SHA-256
  ├─ blobs 中已存在 → 不复制字节；documents 已存在则直接建引用关系
  │                    提示："已存在相同文件（预算表.xlsx），是否建立新的引用关系？"
  └─ 不存在 → 复制一次进 blobs，登记 source_path（记住它从哪来）
```

同时用**文件名 + 大小 + 修改时间**做一层"疑似重复"软提示（哈希不同但内容近似，例如同一份文件改了一个字），避免把近重复材料误判成两份不同议题材料。

### 5.3 原始文件保护（不可妥协）

- `blobs/` 内的文件**只读**，任何流程都不写入、不重命名、不覆盖、不删除（除非用户显式清除且确有引用）
- 应用从不修改用户的原始文件；"打开原文件"默认打开库内副本，另提供"打开来源位置"（只读打开）
- 重命名只改数据库里的 `filename_display`，不动磁盘文件名 → 用户改 100 次名字也不影响文件本身

## 6. 议题 / 附件关系模型

### 6.1 结构

```
会议
├── 会议议程            role = agenda
├── 第一议题            role = first_item
│     ├── 主材料         role = main
│     └── 附件           role = attachment  (attachment_label = "附件1")
└── 人事处议题          kind = department
      ├── 主材料         role = main
      ├── 附件1          role = attachment  label="附件1"  parent_document_id=主材料
      ├── 附件2          role = attachment  label="附件2"
      └── 附件3 人员名单.xlsx（也可被 财务处议题 同时引用）
```

### 6.2 规则

1. **附件永远挂在议题下，不与主材料平级。** UI 上必须缩进显示，并明确"这是 人事处议题 的附件"。
2. **一个议题可以没有主材料**（例如"其他材料"类）。一个议题理论上可有多个主材料（如"1.请示 + 2.报告"），但界面上默认折叠为一个"主材料"分组。
3. **排序**由 `order_index` 决定，间距用 1000 便于插入；拖拽即改。
4. **附件编号**：`attachment_label` 独立字段。自动识别（"附件1"/"附件一"/"附件A"/"附表2"）→ 生成 → 用户可任意改写。自动编号只在**同一议题内**保证唯一。
5. **同一份文件被多个议题引用**：`topic_documents` 两行，UI 在该文件上显示"↗ 也被 财务处议题 引用"，点击可跳转。删除一个引用不影响另一个。
6. **拖拽操作映射**：

| 操作 | 数据库变化 |
| --- | --- |
| 拖到议题下 | insert `topic_documents(role=attachment)` |
| 议题间拖拽 | update 该行 `topic_id` + 重算 `order_index` |
| 拖出附件区 | 改为 `role=other`（成为独立材料），或删除该关系行 |
| 设为主材料 | update `role=main` |
| 取消附件关系 | delete 该关系行（文件仍在会议内，回到"未归类"） |

7. **AI 建议 ≠ 结构变更**：`ai_suggestions` 表先落建议，UI 弹卡片 `[确认][修改][忽略]`。确认时才写 `topic_documents`，并标 `origin=ai_suggested_confirmed`。

### 6.3 附件关系自动识别的依据（按可信度排序）

| 依据 | 可信度 | 例子 |
| --- | --- | --- |
| 所在目录名（部门/分组） | 高 | `人事人才部/`、`第三季度读书班/` |
| 文件名形如 `会议材料<议题号>-<序号>：标题` | 高 | `会议材料1-1：××情况.docx`（实测样例中的主导模式） |
| 文种词（请示/申报表/方案/函/发言/汇报/名单/议程） | 中高 | `××议题申报表.pdf`、`××征求意见函.pdf` |
| 文件名前缀含"附件N" | 高（若出现） | `附件1：××实施方案.docx`。注：实测样例中**未出现**此写法 |
| 主材料正文出现"附件：1. ××方案 2. ××说明"且能匹配到文件名 | 高 | 正文列出附件名 |
| 主材料正文提到"详见附件" | 中 | 需配合文件名相似度 |
| 文件名与正文中的附件名模糊匹配 | 中 | `关于××的实施方案` ≈ `××实施方案.docx` |
| 同一文件夹且命名连续 | 低 | 仅作排序提示 |

识别结果**永远只是建议**。第一阶段大部分场景靠文件名规则即可覆盖，AI 只用来处理"文件名对不上、正文措辞复杂"的硬骨头。

> 该优先级表已按真实样例校准（见 `docs/01-开发日志.md` 的"样例材料勘察"一节）：
> 实际材料的组织方式主要靠**目录分组 + `会议材料N-M` 编号**，而非"附件N"前缀。

## 7. 本地文件存储方案

### 7.1 目录结构

```
~/Documents/会议材料工作台/                 ← 用户可见、可直接备份/拷贝
├── library/
│   └── blobs/
│       ├── 3f/
│       │   └── 3f8a…c21.pdf                ← 唯一副本，只读，SHA-256 命名
│       └── 9b/
│           └── 9b17…e04.docx
├── meetings/
│   └── 2026-09-28-143022-a1b2/             ← 一场会议一个目录
│       ├── ocr/<document-id>/p0001.json    ← OCR 结果（文本+坐标+置信度）
│       ├── ai/<ai-result-id>.json          ← AI 原始输出（含模型与参数，可复现）
│       └── thumbnails/                     ← 首页/目录缩略图
└── db/
    ├── meetingdesk.sqlite                  ← 主库（WAL 模式）
    └── backup/                             ← 每日自动备份，保留最近 7 份
```

备选：放在 `~/Library/Application Support/MeetingDesk/`（更"规范"但用户看不见）。**建议用前者**——你的场景里"我知道会议材料在哪、能直接拷到移动硬盘"比"符合 macOS 惯例"重要得多。库位置可在设置里修改。

### 7.2 为什么文件不进数据库

几十上百份 PDF/Word/图片，动辄几个 GB。SQLite 里只存**路径 + 名称 + 类型 + 哈希 + 时间 + 关系**；字节永远在文件系统。这样：数据库小（一场会议通常 < 5MB）、备份快、出问题可人工抢救。

### 7.3 自动保存与恢复

- 所有写操作立即事务提交（备注、关系、排序、阅读位置、解析结果都是"改完即存"）
- 应用运行中每天自动 `VACUUM INTO` 一份数据库快照，保留最近 7 份
- 退出时把未落库的任务队列 flush
- 退出时执行 WAL 检查点（`wal_checkpoint(TRUNCATE)`），把预写日志合并回主库，保证"只拷 .sqlite 文件也是完整数据"
- "导出这场会议" = 复制 `meetings/<id>/` + 相关 blobs + 一份可读的 JSON 导出
- 崩溃恢复：WAL 保证事务完整；`reading_state` 恢复阅读位置；`jobs` 表中未完成任务重启后自动续跑

## 8. OCR 方案

### 8.1 分流策略（先判断，再 OCR）

```
PDF → 逐页检查是否已有文本层
      ├─ 有（电子版 PDF）→ 直接用文本层，标记 text_source=text_layer，不 OCR
      └─ 无（扫描件）    → 该页入 OCR 队列
图片（JPG/PNG/WEBP）→ 直接入 OCR 队列
DOCX/XLSX/TXT        → 不需要 OCR
```

这一层分流能省掉大量算力——事业单位的会议材料里电子版 PDF 占大多数。

### 8.2 Adapter 设计

```ts
interface OcrEngine {
  id: 'apple-vision' | 'rapidocr' | 'tesseract'
  name: string
  languages: string[]          // ['zh-Hans', 'en-US']
  capabilities: { tables: boolean, coordinates: boolean, confidence: boolean }
  recognize(input: { imagePath: string, pageNo: number }): Promise<OcrResult>
}
interface OcrResult {
  blocks: { text: string, confidence: number, bbox: [x, y, w, h] }[]
  plainText: string
  engine: string
  engineVersion: string
  elapsedMs: number
}
```

| 引擎 | 平台 | 中文效果 | 安装成本 | 第一阶段 |
| --- | --- | --- | --- | --- |
| **Apple Vision** | macOS | 优（已实测） | 零 | ✅ 默认 |
| RapidOCR (PP-OCRv4 ONNX) | 全平台 | 优 | 需打包约 15MB 模型 | 预留接口 |
| Tesseract | 全平台 | 一般 | 需安装 | 不推荐 |

**第一阶段就用系统 Vision。** 零安装、零模型下载、中文效果好、带坐标与置信度、单页 0.43 秒。跨平台需求出现时再实现 RapidOCR adapter，接口不变。

### 8.3 工程细节

- **并发**：默认 2 个 OCR 任务并行（避免打满 CPU 影响用户），设置页可调
- **缓存键**：`(sha256, page_no, engine, engine_version)` → 重启不重算
- **进度**：分页级进度事件推到前端（"财务处议题.pdf 正在 OCR 12/38 页"）
- **表格**：Vision 只给文本块，不还原表格结构。第一阶段保证**文字可搜**；表格结构化还原（合并单元格、行列对应）列入第二阶段
- **页码保留**：OCR 结果按页存储，页码与 PDF 物理页一致，引用跳转不失真
- **失败处理**：单页失败不影响整文档；标记该页"OCR 失败，可重试"，阅读时提示"此页为扫描件且未识别"
- **实现方式**：Vision 通过 Rust 侧桥接调用（已验证可行）；渲染扫描页为位图后送入识别，结果连同坐标写回 `page_text` 与 `text_blocks`

## 9. 本地 AI 方案

### 9.1 Adapter 设计

```ts
interface LocalAiAdapter {
  id: 'ollama' | 'openai-compatible-local'
  probe(): Promise<{ ok: boolean, models: string[], version?: string }>
  chat(req: {
    model: string
    messages: { role: 'system'|'user', content: string }[]
    jsonSchema?: object        // 结构化输出
    temperature?: number
    signal?: AbortSignal       // 必须支持取消
  }): Promise<{ content: string, usage?: object }>
  stream?(req: unknown, onDelta: (s: string) => void): Promise<void>
}
```

| Adapter | 端点 | 说明 |
| --- | --- | --- |
| OllamaAdapter | `http://127.0.0.1:11434/api/chat` | 推荐，模型管理方便，支持 `format: json` 结构化输出 |
| LocalOpenAiCompatAdapter | 任意 `127.0.0.1` 端点 | llama.cpp server / LM Studio / vLLM 等本地推理服务 |

**模型名不写死**：设置页从 `probe()` 拉取模型列表供选择。默认推荐中文能力好的模型（如 Qwen 系列），仅作界面提示，不硬编码。

### 9.2 网络守卫（硬约束）

所有出站请求只经过 Rust 层一个函数：

```
fn guard(target: &Url) -> Result<()> {
    allow target.host ∈ { "127.0.0.1", "::1", "localhost" } 且 scheme ∈ { http, https }
    else → 拒绝 + 写 net_audit(allowed=false) + 计入"网络请求"统计
}
```

- 除本地 AI 外，代码中不存在任何外部域名
- Tauri 配置关闭 updater、遥测、崩溃上报
- CSP：`default-src 'self'; connect-src 'self' http://127.0.0.1:* http://localhost:*; img-src 'self' data: blob:; script-src 'self'; style-src 'self' 'unsafe-inline'`
- 设置页的"网络请求：0"**来自 `net_audit` 的真实计数**，不是写死的文案
- 提供【离线自检】按钮：主动探测外网后报告"未检测到外网依赖"，配合断网实测与 `lsof -i -P | grep -i MeetingDesk` 形成可验证证据链

### 9.3 AI 任务与输出结构

议题包摘要（主材料 + 全部附件作为一个整体理解）：

```json
{
  "one_line": "一句话说清这份材料讲什么",
  "why_on_agenda": "为什么要上会",
  "main_points": ["主要内容…"],
  "attachment_points": [{ "document": "附件1：××实施方案", "point": "主要说明…" }],
  "decisions_needed": ["需要会议决定…"],
  "key_numbers": [{ "value": "1,280,000 元", "context": "2026年度预算", "citation": 3 }],
  "departments": ["财务处"],
  "watch_points": ["需要重点关注…"],
  "citations": [{ "document_id": 12, "page": 3, "quote": "原文原句…" }]
}
```

### 9.4 防编造：四重机制

1. **系统级规则**（写进 system prompt，且不被材料内容覆盖）
   > 你是会议材料辅助工具。只能根据用户提供的原始材料进行分析。不能编造材料中不存在的事实。不能把推测写成事实。不能把 AI 判断写成会议决定。如果材料中没有相关信息，必须明确说"材料未明确"。
2. **强制引用**：每条实质结论必须附 `quote`；无引用的结论不展示
3. **本地校验**：`quote` 在已抽取文本中做归一化匹配（去空白、全半角统一、标点归一），匹配失败 → `verified=false` → 折叠为"⚠️ 未在原文找到，仅供参考"，默认隐藏
4. **字段缺失显式化**：`owner_dept` / `due_date` 为空 → 界面显示"未明确责任部门""未明确截止时间"，**不允许模型填空**

引用可追溯：`ai_citations` 记录 `document_id + page_no + quote`，UI 显示"来源：《关于××的请示》第 3 页"，点击跳转对应页并高亮。

### 9.5 缓存、成本与开关

- 缓存键 `sha256(材料集合哈希 + prompt_version + model + params)`；命中即秒出，不重复烧 CPU
- 生成中可随时取消（AbortSignal + Rust 侧断流）
- 全局开关 + 子开关：`☑ 启用本地AI`、`☐ 自动生成摘要`、`☐ 自动识别议题`、`☐ 自动识别附件关系`
- 未配置时：AI 区域显示"本地AI未配置，阅读/搜索/OCR 等功能不受影响 [如何安装本地AI]"

## 10. 安全与隐私方案

### 10.1 红线（架构级强制，不靠自觉）

| 红线 | 强制手段 |
| --- | --- |
| 不上传会议文件 | 代码中无任何上传接口；唯一 HTTP 客户端受 loopback 白名单约束 |
| 不调用云端 AI/OCR | 无 API Key 概念；OCR 走系统框架；AI 只连本机端口 |
| 不使用远程数据库/云存储 | 无账号体系、无云 SDK 依赖 |
| 断网可用 | 依赖全部本地打包；无 CDN、无在线字体（系统字体栈）、无在线图标（内联 SVG） |
| 不覆盖原始材料 | blobs 只读；重命名只改数据库显示名 |
| 删除可追溯 | 删除进废纸篓而非硬删；二次确认；显示影响范围 |

### 10.2 数据保护

- **第一阶段**：依赖 macOS FileVault（全盘加密）+ 应用数据目录权限（0700）。设置页明确显示"数据加密：依赖系统 FileVault（当前：已开启/未开启）"并主动提示
- **第二阶段可选**：SQLCipher 加密数据库 + 应用启动口令；敏感会议单独加锁与超时自动锁屏
- **日志脱敏**：日志只记录文件名、ID、耗时、错误类型，**绝不记录材料正文**；日志保留上限 7 天

### 10.3 清除功能（都要二次确认，并显示影响范围）

| 操作 | 行为 |
| --- | --- |
| 清除当前会议 | 删该会议的关系与备注；blob 若无其他会议引用则移入废纸篓 |
| 清除全部会议 | 全库重置，保留设置；要求二次确认 |
| 清除 OCR 缓存 | 只删 `meetings/*/ocr/`，保留原文（索引需重建，提示耗时） |
| 清除 AI 缓存 | 只删 `meetings/*/ai/` 与 `ai_results` |

### 10.4 可验证性

隐私承诺必须可验证，不能只是文案：

1. 设置页【离线自检】：断网状态下启动 → 导入 → OCR → 搜索 → 阅读 → 本地 AI 全流程自检并出报告
2. `net_audit` 表记录每一次出站尝试（含被拒绝的）
3. 外部验证方式写进设置页说明：`lsof -i -P | grep -i MeetingDesk` 应无输出

## 11. 技术栈

| 层 | 选型 | 理由 / 备选 |
| --- | --- | --- |
| 桌面壳 | **Tauri 2** | 体积小、Rust 侧可访问系统框架、离线打包干净。备选 Electron（体积大、内存高，但不需要装 Rust） |
| 前端 | **React 19 + TypeScript 5 + Vite** | 生态成熟、类型安全 |
| 状态管理 | **Zustand** | 轻量；无远端数据，不需要 React Query |
| 样式 | **CSS Modules + 设计令牌（CSS 变量）** | 克制可控，不引重型 UI 库；基础交互组件用 Radix Primitives（无样式、可访问性好） |
| 拖拽 | **dnd-kit** | 支持树形排序与文件拖入，键盘可访问 |
| 虚拟滚动 | **@tanstack/react-virtual** | 上百份材料、大表格不卡 |
| PDF | **pdfjs-dist**（worker 本地打包） | 阅读 + 文本抽取 + 坐标，一份库两用 |
| DOCX | **docx-preview**（渲染）+ **mammoth**（提取） | 纯前端，无服务端 |
| XLSX | **SheetJS CE** 解析 + 自研虚拟表格 | 只读查看足够，不引重型表格编辑器 |
| 图标/字体 | 内联 SVG + 系统字体栈 | 零网络依赖 |
| 数据库 | **SQLite（rusqlite, bundled）+ FTS5** | 单文件、事务、全文检索一体 |
| OCR | **Apple Vision**（Rust → 系统框架） | 已实测；跨平台留 RapidOCR adapter |
| 本地 AI | **Ollama**（HTTP loopback）+ 本地 OpenAI 兼容端点 | 模型名不写死 |
| 测试 | **Vitest**（逻辑）+ **Playwright**（关键流程）+ **cargo test**（Rust） | 每个模块自测 |
| 质量 | ESLint + Prettier + rustfmt + clippy | 提交前检查 |
| 打包 | `tauri build` → `.app` / `.dmg`（本地 ad-hoc 签名） | 关闭 updater |

**关于 Rust 的取舍**：本机没装 Rust，这是唯一的额外前置成本（`rustup` 一次性安装，约 5 分钟、约 1GB 磁盘）。换来的是：真正能调用系统 OCR、真正能保证无网络依赖、体积小、启动快。**建议装。**

## 13. MVP 开发计划

原则：**每个里程碑都能独立验收**，验收不过不进入下一个。

| 里程碑 | 内容 | 验收自测（通过标准） |
| --- | --- | --- |
| **M0 环境与骨架** | 安装 rustup；初始化 Tauri 工程；SQLite 迁移框架；CSP 锁定；关闭 updater/遥测；离线自检脚本 | 断网启动空白窗口成功；`net_audit` 为空；`lsof` 无出站连接 |
| **M1 导入与文件库** | 拖拽/选择/整文件夹导入；SHA-256；blobs 落盘；去重提示；保留原文件名；状态列表；删除/重命名/重新解析 | 拖入 30 个文件全部入库；重复文件不产生第二份字节；磁盘核对 blobs 数量正确 |
| **M2 解析与索引** | PDF 文本层抽取；DOCX 标题/正文/表格；XLSX 单元格；TXT；`page_text` 入库；FTS5 trigram；基础搜索 API | 搜"预算"能命中 PDF 第 3 页与 DOCX 段落；中文 2 字词可搜（LIKE 回退） |
| **M3 本地 OCR** | Vision adapter；无文本层页自动分流；分页进度；缓存；失败重试 | 扫描件 PDF 与手机拍的 JPG 均可被搜到；二次导入同文件不重算 OCR |
| **M4 会议结构** | meetings/topics/topic_documents 落库；目录树 UI；拖拽排序；拖拽建立附件关系；右键菜单全部动作；附件编号编辑 | 把 3 份材料拖到"人事处议题"下形成附件1/2/3；把附件拖到另一议题；同一文件被两议题引用时磁盘仍只有一份 |
| **M5 阅读模式** | PDF.js 阅读（缩放/页码/跳页/文本层高亮）；DOCX/XLSX/图片视图；左目录右材料；快捷键；底部导航；阅读位置保存与恢复 | 关掉应用重开，回到"人事处议题第 3 页、缩放 120%"；`Space` 依次翻材料 |
| **M6 备注系统** | 会议/议题/文档/页/段落五级备注；原文-AI-备注三区分离展示；自动保存 | 选中正文加段落备注；重开应用仍在；三种内容视觉上明确区分 |
| **M7 全局搜索** | ⌘K 搜索（原文+OCR+备注+AI+文件名）；结果分组标注来源；点击跳转并高亮命中词 | 搜"预算"出多条结果，来源分类正确，点击准确跳到对应页 |
| **M8 本地 AI 摘要** | Ollama adapter；loopback 守卫；议题包摘要；引用校验；来源跳转；开关与降级 UI | 未装 Ollama 时全部功能正常并提示安装；装了以后摘要每条都有可跳转来源；人为改坏 quote 会被标"未在原文找到" |
| **M9 收尾与打包** | 会议历史/改名/删除；恢复机制；隐私与安全页（真实网络计数、四类清除）；备份导出；`.dmg` 打包；断网全流程演练 | 断网完成"导入→解析→OCR→建立关系→阅读→备注→搜索→AI（若装有）"全流程；清除操作二次确认生效 |

节奏判断：M0–M2 是地基（最需要仔细），M3–M5 是体验主体，M6–M9 是让它变成"能天天用"的工具。

## 15. 风险与已知限制（提前说清，不埋雷）

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| **Word 没有真实"页码"** | DOCX 的页码是排版结果，解析层拿不到 | 第一阶段用"章节 + 段落编号"作锚点，引用标注为"《××》第 2 节"；若本机装了 LibreOffice，可选开启"转 PDF 取真实页码"（纯本地转换） |
| 超大 PDF 渲染卡顿 | WebView 对 500 页以上 PDF 有压力 | 分页懒加载 + 虚拟滚动 + 缩放缓存；M5 用真实大文件压测 |
| DOCX 复杂排版还原度有限 | 表格/文本框/页眉可能失真 | 保底策略：正文+表格视图 + "打开原文件"按钮；不做像素级排版还原（那不是本产品的价值） |
| 扫描件表格结构不还原 | OCR 只出文字 | 文字可搜可引用；结构化留第二阶段 |
| 中文短词检索 | 少于 3 字不走 trigram 索引 | LIKE 回退；必要时追加分词索引 |
| 首次构建需装 Rust | 一次性成本 | rustup 约 5 分钟；之后开发与网页开发的热更新体验一致 |
| 本地模型质量参差 | 摘要可能不够好 | 模型可切换、结果可关闭、永远以"建议"呈现，引用校验兜底 |

## 17. 第一阶段具体开发什么（确认后的第一批动作）

**第一步（M0，约 0.5 天）**

1. 安装 `rustup`（需批准一次网络下载）
2. 初始化 Tauri 2 + React + TS 工程骨架，跑通空白窗口
3. 建立 SQLite 迁移框架 + 第一版表结构（第 4 节全部表）
4. 锁定 CSP、关闭 updater/遥测、建立 `net_audit`
5. 落地"离线自检"脚本：断网起应用 → 报告零出站
6. 把已验证的 Vision OCR 脚本收编为 `src-tauri/src/ocr/` 的正式 adapter（含坐标与置信度）

**第二步（M1，约 1 天）**：导入与内容寻址文件库（拖拽、哈希、去重、状态列表）

**第三步（M2，约 1.5 天）**：解析与全文索引（PDF/DOCX/XLSX/TXT）+ 基础搜索

**第四步（M3，约 1 天）**：OCR 接入与自动分流

此后进入 M4（会议结构，这是产品的灵魂）与 M5（阅读模式）。

**同时需要你提供**：一套（可脱敏的）真实会议材料样例——哪怕只有 5~10 个文件。真实材料的文件名习惯（"附件1：××"这类）直接决定自动识别规则的质量，用真实样本校准比凭空设计准得多。

## 18. 贯穿全程的四条纪律（写进开发约定）

1. **每完成一个模块必须自测**，验收标准见第 13 节，不通过不进下一步
2. **不偷偷增加云端服务**：任何网络代码必须过 loopback 白名单，并写入审计表
3. **不擅自改数据模型**：模型变更必须走迁移文件 + 在本文档登记
4. **AI 只做辅助**：AI 输出永远独立存放、永远带来源、永远需要人确认，永远不覆盖原文与人工结果
